# 13 — Measuring plugin quality

**Priority:** P1 (the deterministic rule checker and the AI-reviewer filter are cheap, high-value P0 candidates for 0.3.0) · **Effort:** L (≈ 6–8 days: checker 1, AI filter 1, fresh held-out labelling 2–3, `claude plugin eval` suite 2) · **Depends on:** none to start; consumes 15's rubric items and fixtures, 07's raw mode, 11's anonymise mode

## Problem

The recommended path, the plugin skill where Claude synthesises rules, has
no measurement at all. The only real-data eval scores the heuristic's
candidate extraction, and its held-out split has been read during tuning,
so its numbers flatter us. Nobody can say whether a SKILL.md edit or a
new model makes the rules better or worse. Separately, the CLI counts AI
reviewers posting from ordinary accounts as human reviewers. On express
they produce a third of all candidates.

## Audit findings

- **What exists.** `eval/run-eval.mjs` scores CLI rules against one
  synthetic fixture (`eval/fixtures/typescript-repo*.json`: keyword plus
  must-cite-PR matching). `eval/run-real-eval.mjs` scores comment-level
  extraction on 540 labelled comments (dev: vitest+pnpm; held-out:
  express, commander.js, swr). Both run in CI (`.github/workflows/ci.yml:34-35`).
  Nothing evaluates clusters, rules, or the skill: `grep -rl
  "SKILL|learn-from-reviews" test eval scripts .github` finds only
  `test/cli.test.mjs`, which tests the old `pr-comments-to-skills` bin.
- **Held-out contamination.** Documented in `eval/real/README.md`: three
  changes were prompted by held-out examples, and without them held-out
  scores 65.0% / 52.0% instead of 69.6% / 64.0%. Also,
  `run-real-eval.mjs --verbose` (lines 98-104) prints held-out false
  positives and false negatives next to dev ones, which makes further
  contamination the easy path.
- **Gallery outputs pass a deterministic check.** I wrote a scratch
  checker that parses each `examples/real-repos/*/plugin/.claude/rules/*.md`
  and verifies it against the cached corpus: every quote verbatim in the
  cleaned comment body, quoted author and PR match the comment at the URL,
  ≥ 2 PRs and ≥ 2 reviewers among the citations, frontmatter is only
  `paths`. **14/14 rules pass.** Each gallery output is a single run
  (Opus 5.5, Oct 2026), so run-to-run variance is unknown.
- **Generic rules are visible in the gallery.** For example "Add a test
  for every behaviour change" (vitest) and "Fix the root cause" (pnpm).
  Research finds that generic context files don't improve agent success
  and raise inference cost by more than 20%
  ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)), and a follow-up
  found no measurable correctness effect
  ([HF 2607.27250](https://huggingface.co/papers/2607.27250)). Plan 15
  filters these at generation time. This plan measures it.
- **Baselines from comparable work.** A prompt-based PR-mining skill
  reports that ~2/3 of mined rules survive human curation, and output
  turns to noise below ~50 PRs
  ([Rush](https://rush.be/insights/mining-pr-comments-for-agent-review-rules)).
  Noise is the main reason teams abandon AI review tools
  ([tianpan.co](https://tianpan.co/blog/2026-04-17-ai-code-review-at-scale-false-positive-trap),
  [RedMonk](https://redmonk.com/kholterhoff/?p=356)).
- **`claude plugin eval` fits part of the need**
  ([docs](https://code.claude.com/docs/en/plugin-evals.md)). Cases live
  under `evals/<case>/` (`prompt.md` plus `graders/*.md` or `case.yaml`).
  Each case runs 3× per arm by default in a fresh sandboxed headless
  session. Graders: `regex`, `tool_used`, `tool_order`, `file_exists`
  (free), and `llm`/`baseline` (a judge model votes 3×). **There are no
  custom-code graders.** `context.scaffold_script` seeds the workspace
  (runs only with `--scaffold`). `context.history_file` continues a
  recorded conversation. When Bash is granted it runs under the OS
  sandbox with network limited to granted domains. Native Windows isn't
  supported (use WSL2). CI needs Claude Code plus model credentials
  (e.g. `ANTHROPIC_API_KEY`), `--trust-plugin`, and accepts
  `--max-cost-usd`. Exit 1 means a case fell below `--threshold`; exit 2
  means a partial run. The eval dir can be relocated with
  `"experimental": {"evals": "…"}` in `plugin.json`. Not verified:
  whether a sandboxed run can execute `${CLAUDE_PLUGIN_ROOT}/bin/*.mjs`
  when the plugin is loaded from a path target.
- **AI reviewers from user accounts.** `isNoise` (`lib/normalize.mjs:83-98`)
  detects bots by `author_type` and a name regex only. I measured a strict
  detector offline (scratch script). It flags a comment when (a) the
  first 200 chars carry a signature ("powered by|generated by … GPT/GLM/
  Claude/Gemini/LLM/AI/model", or "🤖 … review"), or (b) it has a bold
  label (`**Recommendation:**`, `**Severity:**`, `**Impact:**`, …) and a
  severity marker. Applied after the existing filters:

  | Corpus | Flagged | Accounts | Candidates | Candidate clusters | CLI rules |
  |---|---|---|---|---|---|
  | express | 30 (23 signature, 7 bold+severity) | 3 | 368 → 237 (−36%) | 335 → 222 | 0 → 0 |
  | vitest | 1 | 1 | 560 → 557 | 520 → 517 | 3 → 3 |
  | pnpm | 1 | 1 | 382 → 378 | 367 → 363 | 2 → 2 |
  | commander.js / swr | 0 | — | unchanged | unchanged | 0 |

  On `eval/real`: held-out, it removes 1 of the 7 false positives (the
  "Orb Code Review" report) and 0 of the 16 true positives (precision
  69.6% → 72.7%, recall unchanged). Dev: 0/3 false positives, 0/30 true
  positives. Every flagged record in the labelled set is a labelled
  negative.
- **Features that don't work alone** (measured, so excluded): "≥ 2
  headings + ≥ 5 bullets + ≥ 1,500 chars" matches ~20 long *human*
  investigations in the raw vitest/pnpm corpora, mostly from PR authors
  or issue triage. "AI review" anywhere in the body matches humans
  complaining about AI-generated PRs. The signature must sit in the
  opening 200 characters.

## Goals / Non-goals

**Goals:** a held-out set nobody has read. A cheap, deterministic,
key-free check of every rule file the skill writes, run in CI. A
repeatable model-in-the-loop eval of the skill for releases. An
AI-reviewer filter in the CLI with measured impact.

**Non-goals:** gating every PR on model calls. Measuring downstream
agent success with and without rules (a valuable but separate, expensive
study). Perfect AI-text detection.

## Options considered

1. **LLM-judge everything in CI.** Simple to describe, but costly,
   non-deterministic, needs a secret in CI, and forked PRs can't use it.
   Rejected for per-PR CI.
2. **Three layers: deterministic checker (CI), `claude plugin eval` suite
   (release/manual), human checklist (release).** **Chosen.** Cheap where
   it can be, and model judgement only where it's needed.
3. **Our own harness that calls the Agent SDK.** Full control, including
   code graders, but it duplicates `claude plugin eval` and adds a dev
   dependency. Rejected. The deterministic checker covers what code
   graders would.

## Design

### A. Fresh held-out repo for `eval:real`

- **Pre-register before anyone reads data.** Commit
  `eval/real/heldout-2.md` listing 5 candidate repos (different
  language/review culture: e.g. a Go, a Python and a Rust project with
  ≥ 2 active reviewers). Pick one by `sha256(list + date)`, then fetch.
- Sample 200 comments with the existing `sample.mjs` method (new `PLAN`
  entry, split `test2`). Label blind to pipeline output: the labelling
  sheet has no predictions column. A second person labels a random 20%,
  and we report agreement (Cohen's κ). If κ < 0.6, refine the rubric
  before scoring.
- `run-real-eval.mjs`: rename the old held-out split to `test-legacy`
  (still reported). `--check` floors move to `test2` at
  `measured − 5 pts` (never lowered later). `--verbose` lists `dev`
  items only. Held-out items need `--show-held-out`, which prints a
  contamination warning.

### B1. Deterministic rule checker (CI, no keys)

`eval/skill/check-rules.mjs <rules-dir> <candidates.json>`. A candidates
snapshot or raw-mode file is the source of truth. Exit 1 on any failure,
with the output listing `file: check: detail`:

1. File name `pr-feedback-<kebab>.md`. Provenance comment present.
2. Frontmatter absent or exactly `paths:` with quoted globs.
3. ≥ 2 citations, each `> quote` + `— @author|reviewer X on PR #n: url`.
   The URL is in the snapshot, and the author and PR match it.
4. Each quote is verbatim (whitespace-normalised) in the snapshot's
   quote text.
5. ≥ 2 distinct PRs and ≥ 2 distinct reviewers among the citations,
   unless the provenance says `single-maintainer mode` (plan 08: ≥ 3 PRs).
6. Anonymise mode (plan 11): no `@login` anywhere.
7. Scope sanity: every glob is valid and matches ≥ 1 quoted `path`, or
   the rule is unscoped. No glob is limited to docs, changeset or test
   files when the quotes are on source files (SKILL.md step 5).
8. No quote comes from a comment flagged by the AI-reviewer filter
   (the snapshot carries `ai_like: true`).

Snapshots: `eval/skill/snapshots/{vitest,pnpm,express}.candidates.json`,
produced offline from the cached corpora (public data, ~60 KB each). CI
runs the checker over `examples/real-repos/*/plugin`. Today: 14/14 pass.

### B2. Skill eval with `claude plugin eval` (release / manual)

- Location `eval/plugin/` via `"experimental": {"evals": "eval/plugin"}`
  in `.claude-plugin/plugin.json`, so it's not confused with `eval/`.
- **Cases** (one directory each): `vitest`, `pnpm`, `express`,
  `commander-single-reviewer`, `swr-thin`, plus fixtures:
  `ai-reviewer-heavy`, `claude-md-duplicates`, `claude-md-contradicts`
  (both from plan 15), and `non-english` (from plan 07). Each case has a
  `scaffold.sh` that does `git init`, adds `origin`
  (`https://github.com/<o>/<r>.git`), and copies a committed slim corpus
  (plan 05) as `.reviewlore-corpus.json`. That's offline by
  construction. In the sandbox `gh` is unreachable, which is harmless.
- **Turn 1** (`prompt.md`: "Learn our conventions from PR reviews",
  `allowed_tools: [Read, Glob, Grep, Skill]`, run with
  `--allow-tools Bash`). Graders: `tool_used` Skill;
  `tool_used Bash input_match "candidates"`;
  `file_exists ".claude/rules/pr-feedback-*.md" exists:false` (nothing
  written before approval); `regex` on the reply for the proposal table;
  `llm` with the proposal rubric (below).
- **Turn 2** (`context.history_file`: a recorded turn 1 plus "Yes, write
  them all"). Graders: `file_exists` rule files; `regex` on one rule
  file's contents for the citation format; `llm` with the per-rule rubric
  on one file (short input, as the docs recommend for judges).
- **Post-run:** `--keep-temp`, then run the B1 checker over each
  workspace's `.claude/rules/` (the stand-in for the missing code
  graders). `eval/plugin/run.sh` wraps both and writes
  `eval/plugin/results/<date>.json`.
- **Flags:** `--ablation none` (without the plugin the task can't run, so
  Δ means nothing), `--runs 3`, pinned `--model` and `--judge-model`,
  `--max-cost-usd 20` (an estimate, to be calibrated on the first run),
  `--scaffold --trust-plugin`.
- **Where it runs:** locally before each release, and optionally a weekly
  `workflow_dispatch` job with an `ANTHROPIC_API_KEY` secret (owner's
  call). Never on PRs from forks. macOS/Linux only (sandbox requirement).

**Rubric (judge criteria, written as PASS/FAIL).** Per rule: (R1) one
clear, imperative instruction; (R2) every claim in the rule and its
"Why" is supported by the cited quotes, with no invented library names
or rationale; (R3) **repo-specific, not generic best practice**: a
competent engineer new to *this* repo wouldn't do it by default (plan
15); (R4) a convention, not logistics or a one-off design discussion;
(R5) scope matches where the change must be remembered. Per proposal:
(P1) lists dropped clusters with reasons; (P2) asks before writing; (P3)
doesn't count report-style AI reviews as support; (P4) flags conflicts
with existing CLAUDE.md (plan 15 fixtures).

### B3. Human checklist (each release)

`eval/skill/reviews.md`: the owner marks each gallery rule keep / edit /
drop, with a one-line reason. Track the keep rate per release. Rush's
~2/3 is the baseline to beat.

### C. AI-reviewer filter in the CLI

- `lib/normalize.mjs`: export `looksLikeAIReview(body) → reason|null`,
  the strict detector above. In `applySignals`, drop matches after the
  plain-issue step and add `droppedAILike` to `_signalStats`. Flag
  `--keep-ai-reviews` restores them.
- `candidates` and raw mode (plan 07) report the count in `stats`.
- Pattern list in one constant with a comment linking this plan's
  measurements.

## Implementation steps

1. C: `lib/normalize.mjs`, `lib/signals.mjs`, CLI flag, tests, eval
   re-run (update `docs/how-it-works.md` numbers).
2. B1: `eval/skill/check-rules.mjs`, snapshots, `npm run eval:skill`, CI
   step in `.github/workflows/ci.yml`.
3. A: pre-registration file, fetch + sample + labelling (owner time),
   `run-real-eval.mjs` split/flags, floors.
4. B2: `eval/plugin/` cases and scaffolds, slim corpora fixtures (after
   plan 05), `run.sh`, first calibration run, record the baseline.
5. B3: `eval/skill/reviews.md` template, and fill it for current gallery.

## Tests & verification

- `test/normalize.test.mjs`: the detector catches signature and
  bold+severity samples (fixtures written for the test, not copied from
  real accounts). It spares long human investigations, "AI review"
  mid-body, and `**Note:**` alone.
- `test/signals.test.mjs`: `droppedAILike` count; `--keep-ai-reviews`.
- `eval:real` after C: held-out precision ≥ 72% (measured 72.7%), recall
  unchanged.
- B1 self-test: `test/check-rules.test.mjs` with good and bad rule
  fixtures (non-verbatim quote, single PR, a handle in anonymise mode, a
  glob that matches nothing).
- B2 dry run: one case with `--runs 1` to verify scaffolding and sandbox
  access to the plugin's `bin/`.

## Risks, compatibility & rollback

- The AI filter could drop a human who writes structured reports with
  severity labels. Signature/bold+severity only, `--keep-ai-reviews` as
  an escape hatch, and the count is printed.
- Judge variance: 3 votes per grader and 3 runs per case. Treat
  differences under ~10 points as noise until variance is measured.
- Cost: B2 is opt-in and capped. B1 is free.
- `plugin eval` is a recent CLI feature, and its format may change. B1
  doesn't depend on it.

## Cross-cutting checks

- **Credentials:** B2 uses the runner's existing Claude Code credentials.
  Never read them. In CI only via a repo secret, never on fork PRs. Tests
  stay hermetic.
- **Privacy:** snapshots hold public review quotes with handles, as the
  gallery already does. The non-English fixture must come from a public
  repo or be synthetic.
- **Determinism:** the B1 checker and the AI filter are pure. B2 is
  explicitly non-deterministic and reported with ranges.
- **Deps:** none (B2 uses the `claude` CLI, not an npm dep).
- **Windows:** B1 and C everywhere. B2 under WSL2 only.

## Success metrics

- B1 green in CI on every gallery output. Any skill change that breaks it
  is caught pre-merge.
- Fresh held-out: κ ≥ 0.6; floors set; zero tuning commits citing test2
  items.
- B2 baseline recorded: per-case rule count (mean, range), B1 pass rate
  ≥ 95%, R2 (no invented claims) ≥ 95%, R3 (repo-specific) ≥ 90%
  (plan 15's target).
- Human keep rate ≥ 80% per release (Rush baseline ~67%).
- express: AI-like comments are 0 of the cited quotes in plugin output.
