# 10 — Keeping rules fresh

**Priority:** P1 · **Effort:** M (≈ 5 days, estimate) · **Depends on:** 06 (index/search for fresh support), 09's `lib/glob.mjs`; coordinates with 15 (generation-time NEW/DUPLICATE/VIOLATED/CONTRADICTS labels)

_Status (October 2026): implemented. Changes from this design: status
searches with the title words the rule's own quotes share (the full
title made "Add a changeset for every change that ships" match comments
about shipping), requires the rarest of them, and checks contradictions
only for rules recorded with a `--query` (word matching can't tell "fix
at the root cause" from any other "fix"); contradictions suggest "check",
never retirement. `publish-corpus --if-changed` and the Action cache were
already in place (plans 05 and 03). On pnpm, status keeps the changeset
rule (January quotes, 26 PRs of recent support) as "update"._

## Problem

Review culture changes, code moves and conventions die, but rules
generated by the plugin stay as written forever. Re-running
`learn-from-reviews` starts from scratch. It doesn't know which rules it
wrote, which the user edited, or which no longer have support. The
scheduled GitHub Action makes this worse. It regenerates *heuristic* rules
into the same `pr-feedback-*` namespace as the plugin's rules, and opens a
PR every week even when nothing changed.

## Audit findings

- `lib/skill-writer.mjs:138-171` `writeSkills` only adds files. It never
  deletes, so a cluster that is GONE keeps its rule file forever. Without
  `--force` it skips existing files. With `--force` it overwrites them,
  hand edits included. The only provenance is a fixed comment
  (`PROVENANCE`, line 13-14). The plugin uses a variant ending
  `(learn-from-reviews)` (SKILL.md line 120), which is the only way to tell
  the two generators apart. All 14 gallery rules carry it.
- `lib/diff.mjs`: the state file `.claude/.reviewlore-state.json`
  holds `{written_at, clusters:[{label, occurrences, distinctAuthors,
  distinctPRs}]}` (lines 39-53). It is written only by `run`
  (`bin/reviewlore.mjs:514`) and `generate`
  (`bin/commands/generate.mjs:270`), never by `candidates` or the skill.
  Clusters are matched across runs by label-token Jaccard ≥ 0.5 (line 18).
  The ADDED/STRONGER/WEAKER/GONE report goes to **stderr**
  (`bin/reviewlore.mjs:497-498`), so in the Action it ends up in
  the job log, not the PR. It has no link to rule files: no filename, no
  evidence.
- `candidates` cluster ids are positional (`id: c${i + 1}`,
  `bin/reviewlore.mjs:562`), so they can't serve as provenance
  across runs.
- `lib/renderers/_common.mjs:102-105` `clusterId` (sorted label tokens) is
  "stable" only while the vocabulary holds. Plugin rules have no cluster
  at all, since Claude merges several.
- **Evidence ids already exist.** Every rule cites ≥ 2 `html_url`s
  (`#discussion_r…`, `#issuecomment-…`, `#pullrequestreview-…`). Measured:
  all **46 of 46** URLs cited by the 14 gallery rules resolve to a comment
  in the cached corpora. So evidence tracking needs no new ids.
- **Aged out does not mean gone.** If the pnpm corpus were refreshed today
  (2026-10-27) with the default 6-month window, cited evidence for 4 of the
  5 pnpm gallery rules would fall outside it. That includes
  `pr-feedback-add-a-changeset.md`, whose newest citation is 2026-02-12, and
  it is the repo's most important convention. Retiring on "cited evidence
  missing" would delete the best rule. The cache merge never trims
  (`lib/cache.mjs:58-101`), so older evidence stays available.
- `skills/learn-from-reviews/SKILL.md` step 4 says "If `pr-feedback-<slug>.md`
  already exists, show the difference and ask". The skill has no refresh
  mode and no retire step. Line 138-139 says not to add frontmatter fields.
- `examples/github-action/regenerate-rules.yml` runs `fetch --cache` on a
  fresh runner, so there is no cache and it does a full window fetch
  (README "Cost": about one request per PR). Then it runs `publish-corpus
  --force` and `run --format claude --no-cache --force`, and
  `peter-evans/create-pull-request`. Three issues:
  1. `writeCurrentState` stamps `written_at: new Date()` and the corpus
     re-publishes with a new `meta.fetched_at`, so **every run has a diff
     and opens or updates a PR**, even with no rule changes.
  2. Heuristic rules (titles like "Address: fix / instead") land beside
     plugin rules. `--force` overwrites any same-slug file, including a
     hand-edited plugin rule.
  3. The `--llm` option needs `ANTHROPIC_API_KEY` as a repo secret. It
     synthesises per heuristic cluster, so it still can't find
     paraphrase-only conventions like "changeset" (plan 06 findings).
- Docs (verified 2026-10-27, https://code.claude.com/docs/en/memory):
  - "`paths` is the only field Claude Code reads from a rule; any other
    field is ignored without an error. Claude Code removes the frontmatter
    before loading the rule into context."
  - If the YAML doesn't parse, the rule loads "as if it had no `paths`",
    meaning everywhere.
  - Block-level HTML comments are documented as stripped for **CLAUDE.md**.
    For rules this is not stated (unverified).
  - Contradicting instructions: "Claude may pick one arbitrarily". The docs
    recommend periodic review and `/doctor prompt-audit`, which checks for
    "references to files or commands that don't exist" and contradictions.

Related practice (from the coordinator's competitive research):

- GitHub Copilot Memory stores memories with code citations, re-validates
  them against the current branch, and expires them after 28 days
  (https://docs.github.com/en/copilot/concepts/agents/copilot-memory).
- Cursor Bugbot uses a candidate → active → disabled lifecycle with signal
  thresholds and auto-disable (https://cursor.com/blog/bugbot-learning).
  Users ask for learned rules to be promoted into the repo through PRs with
  source links
  (https://forum.cursor.com/t/api-or-git-based-workflow-to-promote-bugbot-learned-rules-into-repository-rules/171018).
- Rush labels mined rules NEW / DUPLICATE / CONTRADICTS / VIOLATED and never
  edits instruction files directly
  (https://rush.be/insights/mining-pr-comments-for-agent-review-rules).
  Plan 15 adopts those labels at generation time. This plan reuses them on
  refresh.

## Goals / Non-goals

Goals: machine-readable provenance for every generated rule (plugin and
heuristic); a `rules status` check that is deterministic and offline; a
skill refresh mode that proposes ADD / UPDATE / RETIRE as a reviewable
diff; hand edits respected; an Action that stops clobbering and stops
opening no-op PRs.

Non-goals: auto-deleting or auto-editing rules, time-based expiry alone,
and touching hand-written rules (no provenance). Running Claude in CI is
optional (below).

## Options considered

**Where provenance lives**

1. **Extra frontmatter key** (`reviewlore: {…}`). Documented as
   ignored and removed before load, so it costs no context. But a YAML
   mistake (often from a hand edit) drops `paths` and the rule loads
   everywhere, and the skill text already forbids extra fields.
2. **JSON in an HTML comment** in the body. Self-contained, but stripping
   isn't documented for rules, so it may cost about 100–300 tokens per rule
   in every matching session (unverified).
3. **Sidecar manifest (chosen).** One committed JSON file next to the rules,
   keyed by filename. It costs no context, carries no YAML risk and is
   diffable in PRs. Its weakness is drift when files are renamed or deleted
   by hand; reconciliation handles that (below). The existing one-line
   marker comment stays as the human-visible signal.

**What the scheduled Action does**

1. Keep heuristic regeneration (status quo). Cheap, but low quality,
   collides with plugin rules and churns weekly.
2. `--llm` in CI. It needs an API key secret and still works per heuristic
   cluster.
3. **Refresh the corpus and report staleness only (chosen default).** The
   Action fetches, publishes the corpus only when the set of comment ids
   changed, runs `rules status`, and opens a PR (or updates one) only when
   the corpus or the status changed. The PR body is the status report.
   Synthesis stays in a developer's session (`learn-from-reviews` refresh
   mode), which needs no key in CI. The heuristic template remains as
   `regenerate-heuristic-rules.yml` for teams without the plugin, with the
   guards below.

## Design

### Manifest: `.claude/reviewlore-rules.json` (committed)

```jsonc
{
  "version": 1,
  "repo": "pnpm/pnpm",
  "rules": {
    "pr-feedback-add-a-changeset.md": {
      "generator": "learn-from-reviews",        // | "heuristic" | "heuristic+llm"
      "status": "active",                        // | "retired"
      "created": "2026-05-17", "refreshed": "2026-05-17",
      "tool_version": "0.3.0",
      "corpus": { "since": "2025-11-17", "fetched_at": "2026-05-17T14:58:11Z" },
      "globs": [],                               // copy of frontmatter paths at write time
      "query": "changeset",                      // search terms for re-finding support (written by the skill)
      "evidence": [ { "url": "…#issuecomment-3591698998", "pr": 10246, "author": "zkochan", "at": "2026-02-12" } ],
      "support": { "prs": 5, "reviewers": 3 },
      "sha256": "…"                              // of the file as written (LF-normalised)
    }
  },
  "dismissed": [ { "title": "…", "evidence": ["url", "…"], "at": "2026-06-01", "reason": "deleted-by-user" } ]
}
```

- The file name is new and separate from the heuristic state file, so it
  never churns. It is written only when content changes (no `written_at`).
  Keys and arrays are sorted.
- `.claude/.reviewlore-state.json` keeps its role (heuristic
  cluster diff) but drops `written_at` churn: the write is skipped when the
  clusters are equal.

### CLI: `reviewlore rules` (new subcommand, offline)

- `rules record <file…> [--generator learn-from-reviews] [--query "…"]`
  parses each file: `paths` frontmatter, the title, cited URLs. It looks
  the URLs up in the cache or corpus (for `pr`, `author`, `at`), computes
  `sha256` and support, and upserts the manifest. The skill calls this
  right after writing, so Claude never hand-writes JSON or hashes.
- `rules status [--json] [--months 6]` evaluates each manifest entry and
  each `pr-feedback-*.md` file without an entry:

| check | how | flag |
|---|---|---|
| file present | fs | `missing` → offer to move it to `dismissed` (the user deleted it) |
| hand-edited | sha256 mismatch | `edited` (never overwritten; updates proposed as a patch) |
| paths still exist | `git ls-files` × `lib/glob.mjs` | `paths-gone` (0 matches), `paths-partial` |
| cited evidence | URLs in corpus; in window? | `evidence-aged-out` (informational only) |
| fresh support | `searchIndex(query + title)` scoped to globs, in window: distinct PRs/reviewers of request/prohibition hits | `active-support {prs, reviewers, latest}` / `no-recent-support` |
| contradiction | in-window hits with negative polarity (`NEGATIVE_TRIGGER_RE` in `lib/cluster.mjs`) from ≥ 2 reviewers | `contradiction-candidates [urls]` |
| unmanaged | `pr-feedback-*` file with no entry | `unmanaged` (pre-0.3 output; `rules record` adopts it) |

  Output is a markdown report on stdout (or JSON with `--json`). The exit
  code is 0 whatever is found. Fresh-support counts are lexical, so they
  are labelled "approximate" and may undercount paraphrases. That is why
  status only *flags* and never retires on its own.

### Skill: refresh mode in `learn-from-reviews`

Triggered when the manifest exists or the user says "refresh/update my
review rules". The description gains "refresh" phrasing.

1. Run `rules status --json` and `candidates` (as today).
2. Classify each existing rule:
   - **KEEP**: support in window, or aged-out evidence with no
     contradiction.
   - **UPDATE**: globs drift (`paths-partial`), better or newer quotes, or
     a support change. Built as a patch to the file. For `edited` files,
     only the Evidence section is patched, and only with the user's OK.
   - **RETIRE (proposal)**: any of `paths-gone`, a contradiction confirmed
     by Claude reading the quotes (≥ 2 reviewers, newer than the rule's
     newest evidence), or `no-recent-support` for ≥ 12 months together with
     the user's confirmation. Never on age alone (the changeset rule
     above).
3. Classify new groups as **ADD**, applying plan 15's NEW / DUPLICATE /
   CONTRADICTS / VIOLATED labels against existing files. Skip anything in
   `dismissed` unless its support has at least doubled; if so, say "you
   removed this on <date>".
4. Show one table (status, rule, reason, evidence links), then the unified
   diff of every change (`git diff --no-index` style), and ask. Write only
   the approved items. Retiring deletes the file (git history keeps it) and
   sets `status: "retired"`. Then run `rules record` for touched files.

### Action changes (`examples/github-action/`)

- New default `refresh-review-corpus.yml`: fetch, then `publish-corpus
  --if-changed` (new flag: skip the write when the comment-id set and
  bodies are unchanged), then `rules status > "$RUNNER_TEMP/status.md"`,
  then create-pull-request with `body-path: $RUNNER_TEMP/status.md`. The
  PR title is "Review-history refresh: N rules need attention" when flags
  exist. That gives the "promote through a PR with source links" flow
  without a key.
- Add `actions/cache` for `~/.reviewlore` keyed by repo, so
  fetches are incremental. Saves about 1,000 requests on busy repos
  (estimate from the brief).
- `regenerate-heuristic-rules.yml` (renamed). `run` gets a guard: never
  overwrite or write a slug whose manifest `generator` isn't heuristic,
  even with `--force`, and print which files were protected.

## Implementation steps

1. `lib/rules-manifest.mjs` (new): load, save (sorted, skip if equal),
   parse the rule file (frontmatter `paths`, title, URLs), and sha256 via
   `node:crypto`.
2. `lib/rule-status.mjs` (new): the checks above, using
   `lib/review-index.mjs` (06) and `lib/glob.mjs` (09).
3. `bin/reviewlore.mjs`: `rules record|status` subcommands and
   HELP. `run`: the protection guard and manifest entries for heuristic
   writes (`generator: "heuristic"`).
4. `lib/diff.mjs`: skip the write when equal and drop the `written_at`
   churn. Keep `written_at` only when the clusters change.
5. `lib/corpus.mjs` and `runPublishCorpus`: `--if-changed`.
6. `skills/learn-from-reviews/SKILL.md`: refresh mode, `rules record` after
   writes, and a "Rules generated by this tool are tracked in
   `.claude/reviewlore-rules.json`" note.
7. `examples/github-action/`: the new template, the renamed heuristic
   template, and the README.
8. `scripts/check-pack.sh`: add the new lib files. Tests. Docs.

## Tests & verification

- Manifest: round-trip determinism; no write when equal; sha mismatch →
  `edited`; a missing file → `missing`.
- Status: fixture repo (temp git with files) plus fixture corpus, covering
  `paths-gone`, `evidence-aged-out` with in-window support (KEEP), and a
  negative-polarity pair → `contradiction-candidates`. A fixed `now` is
  injected.
- Guard: `run --force` doesn't touch a file whose manifest generator is
  `learn-from-reviews` (CLI test).
- `publish-corpus --if-changed`: a no-op when ids are equal (mtime
  unchanged).
- Manual: copy the pnpm gallery rules into a scratch repo, then run
  `rules record` and `rules status --months 6` against the cached corpus.
  Expect the changeset rule to show `evidence-aged-out` but not be proposed
  for retirement.

## Risks, compatibility & rollback

- Pre-0.3 rules have no manifest. They show as `unmanaged`, and
  `rules record` adopts them. Nothing breaks.
- A team that doesn't commit the manifest gets no shared refresh state.
  Docs say to commit it, and it holds only URLs and handles that are
  already in the rule files.
- Lexical fresh-support undercounts, so status never retires by itself.
- Rollback: the manifest is additive. Deleting it returns to today's
  behaviour, and the old Action template stays available.

## Cross-cutting checks

- **Credentials:** `rules` is offline and never resolves a token. The
  Action uses the workflow `GITHUB_TOKEN` only, with no Anthropic key by
  default.
- **Privacy:** the manifest repeats handles and URLs already in rule files.
  `publish-corpus` secret redaction stays as it is.
- **Determinism:** sorted JSON, explicit dates (no wall-clock writes unless
  content changed), injected `now` in tests.
- **Dependencies:** none (`node:crypto`, `git` CLI).
- **stdout/stderr:** reports go to stdout, progress to stderr.
- **Windows:** LF-normalise before hashing, and use POSIX globs.
- **Plugin vs CLI:** both write manifest entries with different
  `generator` values. Only the plugin path synthesises.

## Success metrics

- The Action opens zero PRs on weeks with no new comments (verify on a fork
  over 2 weeks).
- 0 plugin-generated rules overwritten by `run --force` (test).
- On the gallery replay: no retirement proposals for rules with in-window
  support. `paths-gone` precision is 100% on fixtures.
- Refresh session: the user sees a table plus diff, and writes happen only
  after approval (skill eval transcript check).
